# 證據與結論規則

在第 1 階段（擷取）開始前讀本檔；第 3–6 階段寫結論時對照使用。

## 目錄
1. 為什麼需要這些規則
2. 證據 ID
3. 證據等級 E1–E5
4. 結論層級 O / I / H / VP / DP
5. 模式（Pattern）的判定
6. 設計系統推論
7. 常見錯誤

## 1. 為什麼需要這些規則

網站研究最常見的失敗是「描述＋形容詞」：列出看到的東西，再加上「很高級」「很流暢」這類無法驗證的評語。讀者無法分辨哪些是事實、哪些是研究者的猜測，研究也就不能被重複或反駁。
下面的規則讓每個結論都能回答兩個問題：**你怎麼知道？有多確定？**

## 2. 證據 ID

所有證據都登記在 `observations.md` 的證據清單，每筆一個 ID。報告裡只引用 ID，不重貼內容。

| 前綴 | 來源 | 範例 | 怎麼產生 |
|---|---|---|---|
| `S-` | 截圖 | Firecrawl 切圖：`S-d03`（桌機第 3 段）、`S-t01`、`S-m02`；Playwright 截圖：`S-pw1440-hero`、`S-pw390-sec03`、連拍的單張 `S-pw1440-load-07` | 切圖記下原圖 y 範圍；Playwright 截圖的 ID 本身帶寬度，檔案放 `screenshots/pw/` |
| `P-` | 像素取樣 | `P-04` | `capture_tools.py sample`，記下座標與色碼 |
| `M-` | 頁面文字 | `M-L42`（source/page.md 第 42 行） | Firecrawl markdown 存成檔案後引用行號 |
| `B-` | branding 自動萃取 | `B-colors.primary`、`B-typography.fontSizes.h1` | Firecrawl branding 存成 source/branding.json |
| `C-` | computed style、CSS 變數 | `C-h1`、`C-button.primary`、`C-var.--color-bg` | Playwright `getComputedStyle` 或讀 `:root` 的 CSS 變數（網站可直連時）。記下 viewport 寬度 |
| `H-` | 原始 HTML／CSS／JS／檔名線索 | `H-01`（例如 `fallback-dark-glow.webp`）、`H-js-preloader`（程式碼裡的動畫設定值） | markdown 的圖片網址、meta、links；下載的 CSS／JS 摘錄。程式碼裡的 duration、easing 是**設定值**，不是量到的實際播放 |
| `I-` | 互動紀錄 | `I-03`（hover 導覽列後出現下拉） | Playwright 操作或在瀏覽器內定時連拍（E1），或比對 Firecrawl 不同時間的截圖（E3）。`I-` 是「發生了什麼變化」的結論，連拍的每一張是 `S-`，`I-` 引用它們（例如「I-04：S-pw1440-load-03→07 標題升起」）。連拍只能證明「有變化、先後順序」；時長與 easing 要從 computed `transition`、Web Animations API 或錄影逐格量到才算實測 |
| `X-` | 缺口 | `X-02`（截圖 y≥2716 空白） | `capture_tools.py blank`，或無法取得的資料 |

`X-` 很重要：記下「看不到什麼」，第 6 階段的自我審查會用到。

## 3. 證據等級 E1–E5

| 等級 | 意義 | 典型來源 |
|---|---|---|
| E1 | 瀏覽器實際算出或實際操作到的 | `C-`、Playwright 產生的 `I-` |
| E2 | 網站原始碼或檔案直接寫明的 | `H-`、`M-` |
| E3 | 對渲染結果的直接量測 | `P-`、截圖上量的像素尺寸 |
| E4 | 工具自動推估的 | `B-`（branding 是啟發式萃取，可能和畫面不符） |
| E5 | 研究者目測或推算的 | 從截圖比例推估的字重、行高、網格欄數 |

規則：
- 同一件事有多個來源時，引用最高等級的；來源互相矛盾時（例如 branding 主色在畫面上幾乎沒出現），**兩個都記下來並說明矛盾**，不要默默挑一個。
- E5 只能支撐 H，不能支撐 O。

## 4. 結論層級

每個結論句前面加上層級標記，句末附證據 ID。

| 標記 | 層級 | 要求 | 範例 |
|---|---|---|---|
| `[O]` | 觀察 | 直接看到或量到的事實，至少 1 個 E1–E4 證據 | `[O]` 背景色是 `#08090A`（P-01, B-colors.background） |
| `[I]` | 詮釋 | 解釋觀察的功能或理由，引用它根據的 `[O]` | `[I]` 只在見證卡用高彩度，讓社會證明成為長頁面的視覺高潮（依據 O：P-07, S-d06） |
| `[H]` | 假設 | 沒有直接證據的推論；**寫出怎樣才能驗證** | `[H]` 下半頁是捲動才淡入（X-02, M-L88–140）；驗證：Playwright 捲動後截圖 |
| `[VP]` | 已驗證模式 | 同一結構／處理方式出現 ≥2 處獨立位置，逐一列出 | 見第 5 節 |
| `[DP]` | 設計原則 | 從 ≥1 個 VP（或多個 I）抽象出、可遷移到其他網站的原則，引用來源 VP | `[DP]` 把彩度當成稀缺資源，只留給要被記住的訊息（VP-02） |

升級規則：
- `[H]` 不能直接升級成 `[DP]`。只有被驗證（變成 O）或被多處觀察支撐（變成 VP）後才能。
- 主觀評語（「高級」「流暢」「好用」）一律改寫成 `[I]`：說清楚是哪個觀察、造成什麼效果。

## 5. 模式（Pattern）的判定

模式是**重複出現的設計決策**，不是元件名稱。「卡片」「按鈕」「導覽列」不是模式；「每個功能區都用『左標題／右說明 → 產品畫面 → 功能清單』的同一套結構」才是。

可以成為模式的五種重複：
1. 重複的結構（區塊的組成與順序）
2. 重複的互動（同一種回饋或觸發方式）
3. 重複的視覺處理（例如「彩度只出現在產品畫面裡」）
4. 重複的響應式行為（例如「多欄在手機一律改成橫向滑動」）
5. 重複的 UX 決策（例如「每段都同時提供自助與業務兩條 CTA」）

每個模式的寫法：

```
### VP-01 <名稱>
- 類型：結構／互動／視覺處理／響應式行為／UX 決策
- 出現位置：<位置 1>（證據 ID）、<位置 2>（證據 ID）…（至少 2 處）
- 不變的部分：<每次都一樣的規則>
- 會變的部分：<允許變化的地方>
- 推測目的：[I] 或 [H]
```

## 6. 設計系統推論

從渲染結果只能**推論**網站可能有哪些 tokens、foundations、components、variants、states，不能斷言網站有正式設計系統。

- 每一項都標 `[H]` 或 `[I]`，並寫出根據：例如「間距都是 4 的倍數（B-spacing.baseUnit、S-d02 上量到 8／16／24）」。
- 至少辨識兩類：tokens（色彩、字級、間距、圓角）與 components／variants（例如主要／次要按鈕）。
- 看得到 states 才寫（hover、focus、disabled、選中）；看不到就記成 `X-` 缺口。

## 7. 常見錯誤

| 錯誤 | 改法 |
|---|---|
| 「這個網站很高級」 | 拆成 `[O]`（具體色彩、字重、留白數值）＋`[I]`（這些造成的效果） |
| 「動畫很流暢」 | 用動態維度描述（見 analysis-dimensions.md），看不到就寫 `[H]` 與驗證方法 |
| 「視覺美感 5 分」 | 刪掉。沒有評分依據的數字就是主觀評語 |
| 把 branding 的數值當事實 | branding 是 E4，和畫面衝突時要說明 |
| 一個觀察就叫模式 | 不足 2 處就只是 `[O]` 或 `[I]` |
| 比較報告重抄各站資料 | 引用各站報告的段落或 VP 編號 |
| 寫「不刪區塊」「沒有裁切」「全部都…」這類絕對或否定的說法 | 這類說法只要一個反例就不成立。寫之前逐一檢查每個出現位置；有例外就寫出例外，或改成「多數…，例外是…」 |
